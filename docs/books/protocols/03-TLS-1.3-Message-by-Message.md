# 3. TLS 1.3, Message by Message

*Every time a browser shows a padlock, TLS has run. It protects web pages,
email between servers, app traffic, software updates, and the connections
between the machines inside data centers. This chapter takes the current
version, TLS 1.3, apart one message at a time, using the real bytes of the
example handshake that the IETF published in RFC 8448. You will parse the
ClientHello by hand, compute the whole key schedule with HKDF and check every
secret against the published values, build the record layer's nonces, and
watch early data get replayed across a server farm. Then the newer pieces:
Encrypted Client Hello, and the hybrid post-quantum key exchange that became
the default on the web between 2024 and 2026.*

    **You will learn:**

    - the TLS 1.3 handshake, message by message, and what each message proves;

## 3.1 The problem

*Level: beginner.*

By 2013, TLS 1.2 had been a standard for five years and was in trouble. Not
because its core was broken, but because it carried twenty years of options,
some of them disastrous. A server could still pick RSA key transport, which has
no forward secrecy; CBC encryption with MAC-then-encrypt, which had produced a
string of padding-oracle attacks; RC4, whose biases were now practical to
exploit; compression, which leaked secrets through lengths; renegotiation,
which had just needed an emergency fix; export-grade "40-bit" cipher suites
that were supposed to have died in 2000; and a negotiation that the attacker
could, in several cases, push down to the weakest option both sides still
supported. [Chapter 4](04-Thirty-Years-of-TLS-Attacks.md) tells those stories.
The handshake also took two round trips before a client could send its
request, and on mobile networks a round trip could take a quarter of a second.

The IETF's TLS working group began a new version in 2014, with Eric Rescorla,
then at Mozilla, as editor. The goals were short: remove everything
known to be weak or unnecessary, encrypt as much of the handshake as possible,
complete the handshake in one round trip (and allow zero round trips for
returning clients), and get the design analyzed by cryptographers *before*
publication, not after. That last goal was new. Academic teams built formal
models of the drafts in Tamarin and ProVerif and wrote computational proofs of
the key schedule; the miTLS team built a verified implementation alongside.
Several problems were found and fixed in drafts, years before deployment.

It took 28 drafts and four years. Some of the delay was not cryptography at
all. When browsers tried early drafts on the real Internet, a few percent of
connections failed: "middleboxes", the firewalls and proxies that inspect
traffic, broke on anything that did not look like TLS 1.2. The final design
dresses up as TLS 1.2 on the wire, with fields that exist only to keep those
boxes calm. TLS 1.3 was published as RFC 8446 in August 2018. Within two years
it carried most browser traffic.

## 3.2 The handshake at a glance

*Level: beginner.*

A full TLS 1.3 handshake, for a client that has never talked to this server
before, is one round trip. The client speaks first, guessing which key
exchange the server will accept and sending its share at once. Messages in
braces are encrypted.

<div class="mars-steps" markdown>

1. **ClientHello** (client to server, in the clear). A 32-byte random value,
   the cipher suites the client accepts, the TLS versions it supports, the
   key-exchange groups it supports, a **key share** for one or two of them
   (its guess), the signature algorithms it accepts, and the name of the site
   (`server_name`).
2. **ServerHello** (server to client, in the clear). The server's random
   value, the chosen cipher suite, and its own key share in the chosen group.
   Both sides now compute the Diffie-Hellman secret and derive **handshake
   keys**. From here on, everything is encrypted.
3. **{EncryptedExtensions}**. The rest of the server's answers: which
   application protocol (HTTP/2 or HTTP/1.1, by ALPN), record size limits,
   and so on.
4. **{CertificateRequest}**, only if the server wants a client certificate.
5. **{Certificate}**. The server's certificate chain (Chapter 2).
6. **{CertificateVerify}**. A signature, with the certificate's key, over the
   hash of the whole transcript so far.
7. **{Finished}** (server). An HMAC over the transcript, under a key derived
   from the handshake secret. The server may now send application data.
8. **{Finished}** (client), after the client checks the chain, the name, the
   signature and the server's Finished. With it, the client may send its
   first request, encrypted under **application keys**.

</div>

Hold this up against Chapter 1. The two key shares are an ephemeral
Diffie-Hellman, so the session is forward secret. CertificateVerify is the
**signature** of SIGMA: the server signs a transcript that contains both
shares. The Finished messages are the **MAC** of SIGMA: they prove the sender
knows the new key, and since they cover the transcript, which includes the
certificate, they bind the server's identity to that key. Every check covers
the full transcript hash, so a change to any byte by an attacker, including
the deletion of a strong option from the client's offer, makes the
handshake fail.

### What was removed

TLS 1.3 is mostly a list of things TLS 1.2 had and 1.3 does not:

- **RSA key transport** and **static Diffie-Hellman**: no forward secrecy.
  Every key exchange is now ephemeral (EC)DHE, or a PSK, or a PSK with
  (EC)DHE.
- **Custom Diffie-Hellman groups**: servers used to send their own prime,
  which clients could not check. Now only named groups (RFC 7919's ffdhe
  groups and the elliptic curves).
- **CBC mode, RC4, 3DES, MD5, SHA-1 in signatures**, and every cipher that is
  not an AEAD. There are five cipher suites left, all AEADs: AES-128-GCM,
  AES-256-GCM, ChaCha20-Poly1305, and two AES-CCM variants for small devices.
- **Compression** at the TLS layer (CRIME).
- **Renegotiation** (replaced by a narrower KeyUpdate and post-handshake
  authentication).
- **The ChangeCipherSpec message** as a real protocol step (it survives as a
  dummy, for middleboxes).
- **The negotiation of signature algorithms inside cipher suites.** A TLS 1.2
  suite named key exchange, authentication, cipher and hash all at once; a
  TLS 1.3 suite names only the AEAD and the hash, and the rest is negotiated
  separately.

## 3.3 The ClientHello by hand

*Level: beginner.*

RFC 8448 is an unusual RFC: it contains no rules, only complete traces of TLS
1.3 handshakes, every byte and every intermediate secret, so that implementers
can check their code. Its first example is a full handshake between a client
and a server called `server`, with fixed private keys. Here is its 196-byte
ClientHello, taken apart. TLS writes every variable-length field with a length
prefix of one, two or three bytes; the `Reader` class handles that.

```python
# Take apart the ClientHello of RFC 8448 field by field.
h = bytes.fromhex
client_hello = h(
    "010000c00303cb34ecb1e78163ba1c38c6dacb196a6dffa21a8d9912ec18a2ef6283024dece7"
    "000006130113031302010000910000000b0009000006736572766572ff01000100000a001400"
    "12001d001700180019010001010102010301040023000000330026002400"
    "1d002099381de560e4bd43d23d8e435a7dbafeb3c06e51c13cae4d5413691e529aaf2c002b00"
    "03020304000d0020001e040305030603020308040805080604010501060102010402050206"
    "020202002d00020101001c00024001")

EXT = {0: "server_name", 10: "supported_groups", 13: "signature_algorithms",
       28: "record_size_limit", 35: "session_ticket", 43: "supported_versions",
       45: "psk_key_exchange_modes", 51: "key_share", 0xFF01: "renegotiation_info"}
GROUPS = {0x1D: "x25519", 0x17: "secp256r1", 0x18: "secp384r1", 0x19: "secp521r1",
          0x100: "ffdhe2048", 0x101: "ffdhe3072",
          0x102: "ffdhe4096", 0x103: "ffdhe6144", 0x104: "ffdhe8192", 0x11EC: "X25519MLKEM768"}
SUITES = {0x1301: "TLS_AES_128_GCM_SHA256", 0x1302: "TLS_AES_256_GCM_SHA384",
          0x1303: "TLS_CHACHA20_POLY1305_SHA256"}

class Reader:
    def __init__(self, data): self.data, self.i = data, 0
    def take(self, n):
        out = self.data[self.i:self.i + n]; self.i += n; return out
    def num(self, n): return int.from_bytes(self.take(n), "big")
    def vec(self, n): return self.take(self.num(n))      # length-prefixed bytes

r = Reader(client_hello)
print("handshake type", r.num(1), "(1 = ClientHello), length", r.num(3))
print("legacy_version", f"{r.num(2):#06x}", "(0x0303 = 'TLS 1.2', kept for middleboxes)")
print("random", r.take(32).hex()[:16] + "...")
print("legacy_session_id", r.vec(1).hex() or "(empty)")
suites = r.vec(2)
print("cipher suites", [SUITES[int.from_bytes(suites[i:i+2], "big")] for i in range(0, len(suites), 2)])
print("compression", r.vec(1).hex(), "(must be 00: none)")
ext = Reader(r.vec(2))
while ext.i < len(ext.data):
    kind, body = ext.num(2), ext.vec(2)
    note = ""
    if kind == 0:
        note = body[5:].decode()
    elif kind == 10:
        note = ", ".join(GROUPS.get(int.from_bytes(body[i:i+2], "big"), "?") for i in range(2, len(body), 2))
    elif kind == 51:
        note = GROUPS[int.from_bytes(body[2:4], "big")] + " share " + body[6:].hex()[:16] + "..."
    elif kind == 43:
        note = body[1:].hex() + " (0304 = TLS 1.3)"
    print(f"  extension {EXT.get(kind, kind):24s} {len(body):3d} bytes  {note}")
```

```text
handshake type 1 (1 = ClientHello), length 192
legacy_version 0x0303 (0x0303 = 'TLS 1.2', kept for middleboxes)
random cb34ecb1e78163ba...
legacy_session_id (empty)
cipher suites ['TLS_AES_128_GCM_SHA256', 'TLS_CHACHA20_POLY1305_SHA256', 'TLS_AES_256_GCM_SHA384']
compression 00 (must be 00: none)
  extension server_name               11 bytes  server
  extension renegotiation_info         1 bytes  
  extension supported_groups          20 bytes  x25519, secp256r1, secp384r1, secp521r1, ffdhe2048, ffdhe3072, ffdhe4096, ffdhe6144, ffdhe8192
  extension session_ticket             0 bytes  
  extension key_share                 38 bytes  x25519 share 99381de560e4bd43...
  extension supported_versions         3 bytes  0304 (0304 = TLS 1.3)
  extension signature_algorithms      32 bytes  
  extension psk_key_exchange_modes     2 bytes  
  extension record_size_limit          2 bytes  
```

Read the output from the top:

- **`legacy_version` 0x0303** says TLS 1.2. The real versions are in the
  `supported_versions` extension (`0304` = TLS 1.3). TLS 1.2 servers ignore
  extensions they don't know and answer as TLS 1.2; middleboxes see a familiar
  value. Version negotiation through an extension is the main fix for the
  ossification of §3.1.
- **`legacy_session_id`** is empty here. Browsers fill it with 32 random bytes
  in "middlebox compatibility mode", because some middleboxes expected a
  session ID to be echoed.
- **Three cipher suites**, each naming just an AEAD and a hash.
- **`supported_groups`** lists nine groups the client can do; **`key_share`**
  carries an actual X25519 public key for just one of them, its guess. If the
  server picks a group the client sent a share for, the handshake is one round
  trip. A modern browser sends two shares: the hybrid X25519MLKEM768 and plain
  X25519 (§3.10).
- **`server_name`** holds the name `server`, in the clear. This is how one IP
  address serves many sites, and also how anyone on the path learns which site
  you are visiting. §3.9 hides it.
- **`signature_algorithms`** (32 bytes: 15 algorithms) lists what the client
  can verify, ECDSA, RSA-PSS, EdDSA and the rest.
- **`psk_key_exchange_modes`** says that if the client resumes later, it wants
  a fresh Diffie-Hellman too (mode 1, `psk_dhe_ke`), so that resumption keeps
  forward secrecy.

The ServerHello answers in 90 bytes: its random value, the chosen suite
(`1301`, AES-128-GCM with SHA-256), a `key_share` with the server's X25519
public key, and `supported_versions` 0304. Nothing else; everything else is in
EncryptedExtensions.

### The downgrade sentinel

If an attacker strips `supported_versions` from the ClientHello, a TLS 1.3
server would see a TLS 1.2 client and answer in TLS 1.2. Normally the Finished
MACs would catch the edit, but in TLS 1.2 the Finished MACs use whatever
weak algorithms were negotiated. TLS 1.3 adds a second line of defense inside
the server's random value. A TLS 1.3 server that is made to negotiate TLS 1.2
sets the last eight bytes of its ServerHello random to `44 4F 57 4E 47 52 44 01`
(ASCII "DOWNGRD" and 1), or ending in `00` for TLS 1.1 and below. The random
value is covered by the server's signature in every version, so the attacker
cannot remove it, and a TLS 1.3 client that sees it in a TLS 1.2 handshake
aborts.

## 3.4 The key schedule

*Level: intermediate.*

The handshake produces one secret, the Diffie-Hellman output, and needs many
keys: one pair for the handshake messages, another for application data, a
key for each Finished, a secret for resumption, a secret for exporting keys to
the application. TLS 1.2 derived all of these from one "master secret" in ways
that tangled them together (the Finished message was encrypted under keys it
was also helping to authenticate, which made proofs awkward). TLS 1.3 uses a
clean ladder of **HKDF** calls ([Chapter 11 of book 1](../../book/11-Passwords-and-Key-Derivation.md)).

HKDF has two steps. **Extract** takes some input keying material and a salt
and produces a uniformly random pseudorandom key: $\mathrm{PRK} =
\mathrm{HMAC}(\text{salt}, \text{IKM})$. **Expand** stretches a PRK into as
many bytes as needed, tagged with an `info` string so that different uses get
independent keys. TLS 1.3 wraps Expand in its own label format:

$$
\mathrm{HKDF\text{-}Expand\text{-}Label}(S, \ell, c, L)
= \mathrm{HKDF\text{-}Expand}\bigl(S,\ L \,\|\, \texttt{"tls13 "}\ell \,\|\, c,\ L\bigr)
$$

(with each part length-prefixed), and defines
$\mathrm{Derive\text{-}Secret}(S, \ell, M) = \mathrm{HKDF\text{-}Expand\text{-}Label}(S, \ell, H(M), \text{hash length})$,
where $H(M)$ is the **transcript hash** of the handshake messages $M$ so far.
That is the key idea: every secret depends on the transcript up to the moment
it is derived.

The ladder has three rungs, each an Extract:

1. **Early secret** = Extract(salt 0, PSK). With no PSK, the PSK is 32 zero
   bytes. Keys for 0-RTT data and binders for resumption come from here.
2. **Handshake secret** = Extract(Derive-Secret(early, "derived", ""),
   (EC)DHE secret). The client's and server's **handshake traffic secrets** are
   Derive-Secret of this with labels `c hs traffic` and `s hs traffic` and the
   transcript ClientHello...ServerHello.
3. **Master secret** = Extract(Derive-Secret(handshake, "derived", ""), 0).
   The **application traffic secrets**, the **exporter** secret and the
   **resumption** secret come from here, with the transcript through the
   server's Finished (or the client's, for resumption).

From each traffic secret, the actual AEAD key and IV are
HKDF-Expand-Label(secret, "key", "", key length) and (secret, "iv", "", 12),
and the key for a Finished message is HKDF-Expand-Label(secret, "finished",
"", hash length).

### Code it: the key schedule against RFC 8448

This program does the whole computation for RFC 8448's handshake: X25519
between the client's private key and the server's public key (RFC 7748's
Montgomery ladder, in twenty lines), then every rung of the ladder, then the
server's handshake key, IV and Finished key. Each result is compared with the
value printed in the RFC.

```python
# The TLS 1.3 key schedule, checked against the example handshake in RFC 8448.
import hashlib, hmac

def x25519(k, u):                       # RFC 7748, Montgomery ladder (not constant time)
    p, a24 = 2**255 - 19, 121665
    k = bytearray(k); k[0] &= 248; k[31] &= 127; k[31] |= 64
    k, x1 = int.from_bytes(k, "little"), int.from_bytes(u, "little") % 2**255
    x2, z2, x3, z3, swap = 1, 0, x1, 1, 0
    for t in reversed(range(255)):
        bit = (k >> t) & 1
        if swap ^ bit:
            x2, x3, z2, z3 = x3, x2, z3, z2
        swap = bit
        A, B = x2 + z2, x2 - z2
        C, D = x3 + z3, x3 - z3
        DA, CB, AA, BB = D * A, C * B, A * A, B * B
        E = AA - BB
        x3, z3 = (DA + CB) ** 2 % p, x1 * (DA - CB) ** 2 % p
        x2, z2 = AA * BB % p, E * (AA + a24 * E) % p
    if swap:
        x2, z2 = x3, z3
    return (x2 * pow(z2, p - 2, p) % p).to_bytes(32, "little")

def hkdf_extract(salt, ikm):
    return hmac.new(salt, ikm, hashlib.sha256).digest()

def hkdf_expand_label(secret, label, context, length):
    full = b"tls13 " + label.encode()
    info = length.to_bytes(2, "big") + bytes([len(full)]) + full + bytes([len(context)]) + context
    out, block, i = b"", b"", 1
    while len(out) < length:                       # HKDF-Expand, RFC 5869
        block = hmac.new(secret, block + info + bytes([i]), hashlib.sha256).digest()
        out, i = out + block, i + 1
    return out[:length]

def derive_secret(secret, label, messages):
    return hkdf_expand_label(secret, label, hashlib.sha256(messages).digest(), 32)
```

Every value matches. If you change one byte of the ClientHello (try it), the
early secret, handshake secret and master secret stay the same, because the
transcript does not enter those, but every traffic secret and key changes. That
is exactly the property that defeats downgrades: an attacker who edits the
ClientHello leaves the two sides with different keys, and the first encrypted
message fails to decrypt.

Notice also that the master secret is the same for every handshake that used
this Diffie-Hellman secret, regardless of transcript; it is the *traffic*
secrets that bind the transcript. The proofs of the key schedule (§3.13) were
written to show that this layering is sound: each Extract is a "randomness
extractor" step, and each Expand makes independent keys for independent
purposes.

## 3.5 Proving who you are: Certificate, CertificateVerify, Finished

*Level: intermediate.*

After the Hellos, the server sends its certificate chain, encrypted. Then it
proves that it holds the certificate's private key. The **CertificateVerify**
message is a signature over this exact byte string:

- 64 bytes of `0x20` (spaces),
- the context string `TLS 1.3, server CertificateVerify`,
- one zero byte,
- the transcript hash up to and including the Certificate message.

The 64 spaces and the context string are there to make sure the signed bytes
can never be confused with anything else the same key signs: a TLS 1.2
signature, a client's CertificateVerify, a signature in some other protocol
that uses the same certificate. This is **domain separation**, and its absence
caused cross-protocol attacks on TLS 1.2 ([Chapter 4](04-Thirty-Years-of-TLS-Attacks.md)). The client checks the
signature with the public key from the leaf certificate, using one of the
algorithms it offered.

Then the **Finished** message:

$$
\text{verify\_data} = \mathrm{HMAC}\bigl(\text{finished\_key},\ \mathrm{Transcript\text{-}Hash}(\text{ClientHello} \ldots \text{CertificateVerify})\bigr).
$$

The client checks it with the same finished key, which it derived from the
server's handshake traffic secret in the code above. A correct Finished proves
that the server derived the same handshake secret from the same transcript:
key confirmation. Then the client sends its own Finished, keyed from the
client handshake traffic secret.

### Client certificates

If the server wants to authenticate the client (a bank's API, a company's
internal service, a service mesh, [Chapter 5](05-TLS-in-Practice.md)), it sends
**CertificateRequest** before its Certificate. The client answers with its own
Certificate and CertificateVerify, encrypted, before its Finished. Because the
handshake is encrypted by then, a passive listener does not see the client's
certificate, which in TLS 1.2 traveled in the clear and revealed who was
connecting. TLS 1.3 also allows **post-handshake authentication**: a server can
request a client certificate later in the connection, for example when a user
opens a protected page.

### Server-only authentication is the common case

On the web, only the server authenticates in TLS; the client logs in later,
inside the channel, with a password, a passkey (Chapter 13)
or a token (Chapter 14). This means a
TLS session alone proves to the client who the server is, and proves nothing to
the server about the client. Application protocols that need the two linked use
the TLS **exporter** (RFC 8446 §7.5, and the `tls-exporter` channel binding of
RFC 9266): a value derived from the exporter master secret that is the same at
both ends of one connection and different on any other.

## 3.6 The record layer

*Level: intermediate.*

Once keys exist, TLS carries data in **records**: at most $2^{14}$ bytes
(16 KB) of plaintext each, encrypted with the AEAD. Each record is built like
this:

1. The plaintext is followed by one byte giving the real **content type**
   (handshake 22, alert 21, application data 23) and then any number of zero
   bytes of **padding**. This is the `TLSInnerPlaintext`.
2. It is encrypted with the AEAD under the current traffic key, with a
   per-record **nonce** made by XORing the 64-bit record sequence number
   (left-padded to 12 bytes) into the 12-byte IV.
3. The 5-byte header in front always says content type 23 and version
   `0303`, whatever is inside. The header is the AEAD's associated data, so it
   is authenticated.

```python
# The TLS 1.3 record layer: one nonce per record, the content type hidden
# inside the encryption, and why a sequence number must never repeat.
s_iv = bytes.fromhex("5d313eb2671276ee13000b30")   # server handshake IV from RFC 8448

def record_nonce(iv, seq):
    padded = seq.to_bytes(len(iv), "big")          # 64-bit counter, left-padded with zeros
    return bytes(a ^ b for a, b in zip(iv, padded))

for seq in range(3):
    print("record", seq, "nonce", record_nonce(s_iv, seq).hex())

def inner_plaintext(content, content_type, pad):
    return content + bytes([content_type]) + bytes(pad)   # TLSInnerPlaintext

def outer_header(ciphertext_len):
    # every encrypted record claims to be application_data (23), version 0x0303
    return bytes([23, 3, 3]) + ciphertext_len.to_bytes(2, "big")

alert = inner_plaintext(b"\x01\x00", 21, 0)          # close_notify alert
data = inner_plaintext(b"GET / HTTP/1.1\r\n", 23, 13)
for name, inner in [("alert", alert), ("data", data)]:
    print(name, "inner", len(inner), "bytes, header on the wire:",
          outer_header(len(inner) + 16).hex(), "(16 = AEAD tag)")
```

```text
record 0 nonce 5d313eb2671276ee13000b30
record 1 nonce 5d313eb2671276ee13000b31
record 2 nonce 5d313eb2671276ee13000b32
alert inner 3 bytes, header on the wire: 1703030013 (16 = AEAD tag)
data inner 30 bytes, header on the wire: 170303002e (16 = AEAD tag)
```

The sequence number is never sent; each side counts records, and a record that
is dropped, reordered or replayed decrypts with the wrong nonce and fails
authentication. That gives replay protection for free, over a reliable stream.
(DTLS and QUIC, which run over unreliable UDP, have to send the number,
[Chapter 5](05-TLS-in-Practice.md).)

Hiding the content type means a listener cannot tell an alert from data or a
post-handshake message from a request. Padding lets an application hide the
length of a record if it wants to, though few do.

### Limits and key update

Every AEAD has a limit on how much data one key can safely protect, set by its
proof: past it, an attacker's chance of forging a record or distinguishing the
traffic from random rises above the target. RFC 8446 §5.5 sets the limits: for
AES-GCM, $2^{24.5}$ full-size records (about 24 million, or roughly 380 GB)
per key; ChaCha20-Poly1305's limit is far larger. A long-lived connection, like
a database link or a VPN over TLS, will reach the AES-GCM limit, so TLS 1.3
has **KeyUpdate**: either side sends a KeyUpdate message and switches to a new
traffic secret,

$$
\text{secret}_{n+1} = \mathrm{HKDF\text{-}Expand\text{-}Label}(\text{secret}_n,\ \text{"traffic upd"},\ \text{""},\ \text{hash length}),
$$

and the old one is deleted. Because the new secret is a one-way function of the
old, an attacker who steals the current traffic secret cannot work backwards to
earlier traffic: forward secrecy within a session. It does not give
post-compromise security, because the next key follows from the current one;
for that, a fresh Diffie-Hellman is needed, which is the step Signal's ratchet
takes every message (Chapter 16).

## 3.7 When the guess is wrong: HelloRetryRequest

*Level: intermediate.*

The client sends a key share for the group it *guesses* the server prefers.
If the server supports none of the groups the client sent shares for, but does
support another group in `supported_groups`, it answers with a
**HelloRetryRequest**: a ServerHello with a special random value (the SHA-256
of the string "HelloRetryRequest") that names the group it wants. The client
sends a second ClientHello with a share in that group. This costs a round
trip, which is why browsers send two shares.

Two details matter for security. First, the transcript continues across the
retry: the first ClientHello is replaced in the transcript by a special
`message_hash` message containing its hash, so the final signatures cover the
whole exchange, including the retry. Second, the server can put a **cookie** in
the HelloRetryRequest, which the client must echo. A server under a flood of
fake ClientHellos from forged addresses can answer each with a cookie and keep
no state, then continue only with clients that echo it, proving they can
receive packets at their claimed address. This matters for DTLS and QUIC,
where UDP makes forged addresses easy.

## 3.8 Resumption, PSKs and 0-RTT data

*Level: intermediate.*

A returning client should not need a full handshake with certificate checks
and signatures every time. After the handshake, the server sends one or more
**NewSessionTicket** messages. Each contains a **ticket**, an opaque blob, and
a nonce. Client and server each compute a **pre-shared key** from the
resumption master secret and that nonce. The ticket itself is usually the PSK
and some state, encrypted under a key only the server knows, so the server can
recover the PSK when the ticket comes back without storing anything.

Next time, the client sends the ticket in a `pre_shared_key` extension, with a
**binder**: an HMAC, under a key derived from the PSK, over the ClientHello so
far. The binder proves the client really holds the PSK and ties it to this
ClientHello. The server finds the PSK, checks the binder, and the key schedule
starts from that PSK instead of from zeros. With mode `psk_dhe_ke` the client
also sends a key share and the server answers with its own, so the session
gets fresh forward-secret keys; certificates and signatures are skipped.

### 0-RTT: data before the handshake ends

A client resuming with a PSK can do something more: send application data in
its *first* flight, encrypted under a key derived from the early secret, before
the server has said anything. This **early data** (or 0-RTT data) saves a full
round trip on the first request. It has two weaknesses, both stated plainly in
RFC 8446.

**No forward secrecy for the early data.** The 0-RTT key comes from the PSK
alone. If the server's ticket-encryption key is stolen later, recorded early
data can be decrypted. The rest of the session still has forward secrecy if
`psk_dhe_ke` was used.

**Replay.** The early data comes before the server has contributed anything
fresh, so nothing in it can prove it is new. An attacker who records the
client's first flight can send it again, to the same server or to another
server in the same cluster, and the request is processed again.

### Code it: replaying early data

The program below sends one 0-RTT request ("pay Bob 100") and then replays the
same flight twice, once to the same server and once to another server of the
same service, under three policies.

```python
# 0-RTT early data can be replayed. Three ways a server cluster can respond.
import hashlib

def run(policy):
    shared_used = set()                      # one store for the whole cluster
    local_used = {"server-A": set(), "server-B": set()}
    balance = 1000

    def receive(server, ticket, client_hello, early_data):
        nonlocal balance
        if policy == "accept all":
            ok = True
        elif policy == "per-server memory":
            key = hashlib.sha256(client_hello).hexdigest()
            ok = key not in local_used[server]
            local_used[server].add(key)
        elif policy == "single-use tickets":
            ok = ticket not in shared_used
            shared_used.add(ticket)
        if ok and early_data.startswith(b"POST /pay"):
            balance -= 100
        return "accepted" if ok else "rejected 0-RTT (falls back to 1-RTT)"

    hello = b"ClientHello with psk ticket T1 and early_data"
    request = b"POST /pay?to=bob&amount=100"
    print(f"{policy}:")
    print("   client  -> server-A:", receive("server-A", "T1", hello, request))
    print("   replay  -> server-A:", receive("server-A", "T1", hello, request))
    print("   replay  -> server-B:", receive("server-B", "T1", hello, request))
    print("   balance:", balance)

for policy in ("accept all", "per-server memory", "single-use tickets"):
    run(policy)
```

```text
accept all:
   client  -> server-A: accepted
   replay  -> server-A: accepted
   replay  -> server-B: accepted
   balance: 700
per-server memory:
   client  -> server-A: accepted
   replay  -> server-A: rejected 0-RTT (falls back to 1-RTT)
   replay  -> server-B: accepted
   balance: 800
single-use tickets:
   client  -> server-A: accepted
   replay  -> server-A: rejected 0-RTT (falls back to 1-RTT)
   replay  -> server-B: rejected 0-RTT (falls back to 1-RTT)
   balance: 900
```

Accepting everything lets the payment run three times. Each server remembering
what it has seen stops replays to the same machine, but not to the next one
behind the load balancer. Only a store shared by the whole cluster, here one
that lets each ticket carry early data once, stops both, and a shared store
across data centers on several continents is expensive and slow. RFC 8446 §8
discusses these mechanisms (single-use tickets, recording ClientHellos within a
time window, and checking the ticket's age against the client's clock).

The practical rule, set for HTTP by RFC 8470 (2018), is that **0-RTT data
should only carry requests that are safe to repeat**: a `GET` for a public page,
not a payment. A server that receives an unsafe request in early data can
answer `425 Too Early`, and browsers mark early-data requests with an
`Early-Data: 1` header when they pass through a proxy. Many large services
accept 0-RTT only for idempotent requests, and many do not enable it at all.

## 3.9 Encrypted Client Hello

*Level: intermediate.*

TLS 1.3 encrypts the server's certificate, but the ClientHello is still in the
clear, and it contains `server_name`. Anyone on the path (the Wi-Fi operator,
the Internet provider, a national firewall) can read the name of every site
visited, and many censorship systems block by that name. Hiding it is hard for
a reason Chapter 1 named: the client must encrypt before it has talked to the
server, so it needs a public key in advance.

**Encrypted Client Hello** (ECH), published as RFC 9849 in March 2026 after
years of drafts (and an earlier experiment called ESNI), works like this:

<div class="mars-steps" markdown>

1. A provider that hosts many sites behind shared addresses (a content
   delivery network, say) publishes an **ECH configuration** containing a
   public key in DNS, in an HTTPS record (RFC 9848 describes how).
2. The client builds its real **inner ClientHello**, with the real
   `server_name`, and encrypts it to that public key with **HPKE**, the hybrid
   public-key encryption of RFC 9180
   ([Chapter 16 of book 1](../../book/16-PKI-and-Key-Establishment.md)).
3. It sends an **outer ClientHello** that names only the provider's public
   name (for example `cloudflare-ech.com`) and carries the encrypted inner
   hello in an extension.
4. The provider's front-end decrypts the inner hello and continues the
   handshake for the real site. A listener sees only the outer name, shared
   by every site behind that provider.

</div>

Two more mechanisms make ECH useful. **GREASE ECH**: clients that are not
using ECH send a fake ECH extension with random contents, so that a listener
cannot tell real ECH from no ECH, and so that middleboxes learn to tolerate the
extension. (GREASE, "Generate Random Extensions And Sustain Extensibility", RFC
8701, is the general practice of sending random unknown values so that servers
and middleboxes cannot ossify around today's set.) And **retry configs**: if
the server's key has changed, it answers the outer handshake with its new
configuration, authenticated by the public name's certificate, and the client
tries again.

ECH hides the name only if many sites share the outer name, and only if the
DNS lookup that fetched the configuration was itself private
([Chapter 10](10-DNSSEC-and-Private-DNS.md)). It is deployed by Cloudflare
and supported by Chrome and Firefox; some national networks block it outright,
which is itself a choice they must make visibly.

## 3.10 Post-quantum key exchange

*Level: intermediate.*

Chapter 1 explained "harvest now, decrypt later": a quantum computer built in
the future could break today's recorded X25519 exchanges. Key exchange
therefore had to change first, and TLS was the first protocol where it changed
at scale.

TLS 1.3's design made this simple: a key exchange is a `supported_groups`
entry and a `key_share`. A **hybrid** group combines a classical exchange with
a post-quantum KEM ([Chapter 21 of book 1](../../book/21-Lattice-Cryptography.md))
so that the session is secure if *either* holds:

- The client's share for **X25519MLKEM768** (group number `0x11EC`) is an
  ML-KEM-768 encapsulation key (1,184 bytes) followed by an X25519 public key
  (32 bytes): 1,216 bytes, instead of 32.
- The server encapsulates to the ML-KEM key and returns the ciphertext (1,088
  bytes) and its own X25519 share (32): 1,120 bytes.
- The shared secret fed into the key schedule is the ML-KEM shared secret
  followed by the X25519 shared secret, 64 bytes. Nothing else in the
  handshake changes.

Google first tried a post-quantum hybrid in Chrome in 2016 (CECPQ1, with
NewHope), tested hybrids with Kyber from 2023, turned one on by default in
Chrome 124 (April 2024), and switched to the standardized ML-KEM version, X25519MLKEM768,
in late 2024. Firefox, Cloudflare, Apple's systems and OpenSSL 3.5 (2025)
followed. The groups were published in RFC 10024 in August 2026, by which time
they already carried a large share of web traffic. The extra kilobyte in the
ClientHello caused a familiar problem: some middleboxes and servers mishandled
a ClientHello that no longer fit in one packet, and browsers had to work with
vendors to fix them, a repeat of the ossification story of 2017.

Signatures are a harder problem, because post-quantum signatures and keys are
far larger, and there are several of them in each handshake (§2.11 in
[Chapter 2](02-Certificates-and-PKI.md)). They are also less urgent: a
signature only has to be unforgeable at the moment of the handshake, so it
must be post-quantum before a quantum computer exists, not decades before.
Book 5 covers the migration in full.

## 3.11 Mars: is 0-RTT worth it?

*Level: intermediate.*

At the average Earth-Mars distance, one round trip is about 25 minutes, and up to 45 at the farthest
([Chapter 1](01-What-a-Protocol-Must-Do.md), §1.9). For a client on Mars
fetching something from a server on Earth, the gain from 0-RTT is not a quarter
of a second but a quarter of an hour, and the temptation to use it for
everything is strong.

The costs scale too. A replay is still a replay: if an attacker anywhere on the
long path can copy a 0-RTT flight that says "transfer credits", it can deliver
the copy to a second Earth data center, and both may execute it. A ticket's
lifetime is limited (RFC 8446 caps it at seven days), and with a round trip of up to 45
minutes, the ticket-age check against the client's clock needs a window of
tens of minutes, which widens what a recorded ClientHello can be used for.

The answer the protocol suggests is the same as on Earth, applied with more
discipline. Use 0-RTT for requests that are safe to repeat, which, between
planets, can be made most requests: fetch this file, send these sensor
readings, each tagged with an application-level identifier so the receiver
ignores duplicates. Anything that changes state (a payment, a command to a
machine) should travel in a full handshake's 1-RTT data, or better, not in an
interactive session at all, but as a signed, self-contained message with its
own sequence number, the store-and-forward design of
Chapter 20.

## 3.12 In the real world

*Level: intermediate.*

- **Ossification** (2016-2017). When Chrome and Firefox enabled early TLS 1.3
  drafts, connections through certain proxies failed. In February 2017 a
  Chrome update that enabled TLS 1.3 broke Chromebooks in schools using one
  vendor's proxy, and the experiment was rolled back. Measurements by browser
  makers found a few percent of connections failing on some networks. The
  response was the disguise of §3.3 (legacy version, session ID, dummy
  ChangeCipherSpec) and GREASE.
- **The Selfie attack** (2019). Nir Drucker and Shay Gueron showed that when
  two parties share one PSK and each can act as client and server, an attacker
  can reflect a client's messages back to it as if they came from the server,
  because nothing in the PSK handshake said which role each side had. The fix
  is to use different PSKs per direction or to bind identities to the PSK. It
  affects uses like peer-to-peer meshes, not the web.
- **Ticket keys as a weak point.** A 2016 study by Drew Springall, Zakir
  Durumeric and J. Alex Halderman found that many large sites reused the key
  that encrypts session tickets for weeks or months, so stealing that one key
  would decrypt every resumed session in that time, defeating forward secrecy.
  TLS 1.3's `psk_dhe_ke` mode reduces this; the rule is to rotate ticket keys
  often ([Chapter 5](05-TLS-in-Practice.md)).
- **Adoption.** By the early 2020s most HTTPS connections from browsers used
  TLS 1.3. TLS 1.0 and 1.1 were formally deprecated by RFC 8996 in 2021, and
  browsers had stopped accepting them in 2020.

!!! note "Life story: TLS 1.3"
    **Born:** August 2018, RFC 8446, after 28 drafts from 2014; editor Eric
    Rescorla · **Purpose:** a faster, simpler TLS with every weak option
    removed, designed together with formal analysis · **Helped:**
    one-round-trip handshakes, encrypted certificates, forward secrecy for
    everyone, the base of QUIC (RFC 9001) and of ECH and hybrid post-quantum
    key exchange · **Status:** current; the default on the web

!!! note "Life story: 0-RTT early data"
    **Born:** 2018, in TLS 1.3, after Google's QUIC crypto showed the gain;
    HTTP rules in RFC 8470 (2018) · **Purpose:** send the first request with
    no round trip on resumption · **Helped:** faster repeat visits, especially
    on mobile networks · **Status:** current, but replayable by design; used
    for idempotent requests only, and disabled by many services

## 3.13 Going deeper

*Level: expert.*

**Proofs of the handshake.** Benjamin Dowling, Marc Fischlin, Felix Günther and
Douglas Stebila proved draft versions secure in a multi-stage key exchange
model (2015, with later versions covering the final RFC), in which each stage's
key (handshake, application, resumption, exporter) has its own security
guarantee. Cas Cremers, Marko Horvat, Jonathan Hoyland, Sam Scott and Thyla van
der Merwe built a Tamarin model of the draft 21 handshake with all its modes
(2017) and found an attack on an earlier draft's post-handshake client
authentication combined with PSK resumption, which was fixed. Karthikeyan
Bhargavan and colleagues' miTLS project produced verified models and a verified
implementation in F\* of the record layer and handshake.

**Why the transcript is hashed, not concatenated.** Every Derive-Secret takes a
hash of the messages so far, and the HelloRetryRequest replaces the first
ClientHello with a hash too. This keeps the state small, but it also means the
security of the transcript binding rests on collision resistance of the hash:
if an attacker could find two different transcripts with the same hash, it
could make the two sides agree on keys while seeing different messages. With
MD5 and SHA-1 in TLS 1.2's signatures this was a real attack (SLOTH, 2016,
[Chapter 4](04-Thirty-Years-of-TLS-Attacks.md)); TLS 1.3 uses only SHA-256 and
SHA-384.

**External PSKs and importers.** PSKs provisioned out of band (not from a
ticket) are used by IoT devices and some VPNs. RFC 9258 (2022) defines PSK
importers that derive per-protocol, per-hash PSKs from one external key, to
avoid the cross-protocol and Selfie problems. Pure-PSK modes without
Diffie-Hellman have no forward secrecy at all.

**Certificate compression and the size budget.** RFC 8879 (2020) compresses
certificate chains with Brotli or zlib, saving hundreds of bytes per handshake;
it is widely used by browsers. With post-quantum signatures the budget
question returns: KEMTLS and Merkle Tree Certificates (Chapter 2) are the two
leading proposals for keeping the first server flight small.

**What a proof does not cover.** The proofs model the protocol, not every
implementation. State machine bugs (accepting messages out of order, skipping
a check when a message is absent) broke many TLS 1.2 libraries in 2015
("SMACK", Benjamin Beurdouche and colleagues); TLS 1.3's simpler state machine
helps, but the same testing is still required ([Chapter 4](04-Thirty-Years-of-TLS-Attacks.md)).

## Check yourself

??? question "1. Which TLS 1.3 handshake messages travel unencrypted?"

    Only the ClientHello and ServerHello (and a HelloRetryRequest, if any).
    Everything from EncryptedExtensions on is encrypted under handshake keys.

??? question "2. Why does the ClientHello still say version 0x0303 (TLS 1.2)?"

    For compatibility. Servers and middleboxes that only know TLS 1.2 handle
    the message normally; the real versions are listed in the
    `supported_versions` extension, which old software ignores.

??? question "3. What does CertificateVerify sign, and why does it start with 64 spaces and a context string?"

    The transcript hash up to the Certificate message. The prefix and the
    context string (which names the role, server or client) make the signed
    bytes unique to this use, so a signature made by the same key elsewhere
    cannot be replayed as a CertificateVerify, and vice versa.

??? question "4. In the key schedule code, which values stay the same if one byte of the ClientHello is changed, and which change?"

    The early, handshake and master secrets stay the same (they depend on the
    PSK and the Diffie-Hellman secret, not the transcript). Every traffic
    secret, key, IV and Finished key changes, because each is derived with the
    transcript hash.

??? question "5. How is the AEAD nonce of record number 5 built from the IV `5d313eb2671276ee13000b30`?"

    XOR the sequence number 5, written as 12 bytes, into the IV:
    `...0b30` XOR `...0005` = `5d313eb2671276ee13000b35`.

??? question "6. What does KeyUpdate protect against, and what does it not?"

    It limits how much data one key protects and gives forward secrecy within
    the session: stealing the current secret does not reveal earlier traffic.
    It does not give post-compromise security, because each new secret is
    computed from the old one.

??? question "7. Why can 0-RTT data be replayed while 1-RTT data cannot?"

    0-RTT data is encrypted under a key derived only from the PSK and the
    ClientHello, before the server has contributed anything fresh, so nothing
    in it can show the server that it is new. 1-RTT keys depend on the
    server's fresh key share and random value.

??? question "8. A cluster of servers keeps a list of seen ClientHellos per server. Why is that not enough to stop 0-RTT replay?"

    The attacker sends the replay to a different server in the cluster, which
    has not seen it. A store shared by every server that accepts the ticket
    (or single-use tickets) is needed.

??? question "9. What does Encrypted Client Hello hide, and what does it need to work?"

    The real ClientHello, including the server name. It needs the provider's
    ECH public key in advance (from DNS), many sites behind the same public
    name, and private DNS so the lookup doesn't reveal the name anyway.

??? question "10. How large is the client's key share for X25519MLKEM768, and why was key exchange made post-quantum before signatures?"

    1,216 bytes (a 1,184-byte ML-KEM-768 encapsulation key plus 32 bytes of
    X25519). Key exchange protects recorded traffic that a future quantum
    computer could decrypt (harvest now, decrypt later); a signature only has
    to resist forgery at handshake time.

## What you learned

- The TLS 1.3 handshake is a one-round-trip SIGMA: ephemeral key shares,
  a signature over the transcript (CertificateVerify), and MACs over the
  transcript (Finished). Everything after the Hellos is encrypted.
- The key schedule is a ladder of HKDF-Extract steps (early, handshake,
  master), with every traffic secret derived from the transcript at that
  point. You computed it and matched RFC 8448.
- Records carry a hidden content type and padding, and use the IV XORed with
  an implicit sequence number as the nonce. KeyUpdate refreshes keys within
  limits set by the AEAD's proof.
- Resumption uses tickets and PSKs with binders. 0-RTT data saves a round trip
  but can be replayed and lacks forward secrecy; use it only for idempotent
  requests.
- ECH hides the server name using HPKE and a key published in DNS.
- Hybrid X25519MLKEM768 makes the key exchange safe against future quantum
  computers, at the cost of about a kilobyte each way.
